## 1. Spring AI：Java 世界的 LLM 框架

### 是什么
Spring AI 是 Spring 官方的 AI 应用框架，提供统一抽象屏蔽不同模型厂商的差异。核心抽象：

- **ChatModel / ChatClient**：对话模型的统一入口，`ChatClient` 是流式/非流式调用的门面。
- **EmbeddingModel**：文本向量化统一接口。
- **VectorStore**：向量存储抽象（本项目用 PgVector 实现）。
- **Tool Calling**：把 Java 方法暴露给 LLM，让模型"决定调用哪个函数"。
- **Advisor**：拦截器链，可在调用前后插入逻辑（如 RAG 增强、记忆）。

### 项目里的用法
```java
// ChatClient 流式调用 + 工具绑定 + 记忆
chatClient.prompt()
    .system(systemPrompt)
    .user(userMessage)
    .advisors(a -> a.param(ChatMemory.CONVERSATION_ID, conversationId))
    .toolContext(Map.of("conversationId", conversationId))
    .stream().content()          // Flux<String>，逐 token
```

### 坑与进阶
- **坐标变化快**：1.0.0 GA 里 RAG 在 `spring-ai-rag`、`QuestionAnswerAdvisor` 已被 `RetrievalAugmentationAdvisor` 取代——这类框架升级时 API 变动大，要跟紧官方 migration 指南。
- **多模型**：项目里注入了多个 `ChatModel`，必须显式提供 `ChatClient.Builder` 并用 `@Qualifier` 锁定，否则 Spring 因"Bean 不唯一"启动失败。

## 2. RAG 原理与完整流水线

### 是什么
RAG（Retrieval-Augmented Generation，检索增强生成）：先检索相关知识，再让 LLM 基于知识生成，解决 LLM 的"幻觉"和"知识陈旧"问题。

```
离线（入库）：文档 → 解析 → 分块(chunk) → embedding → 向量库
在线（问答）：query → 改写 → 检索 top-k → 拼进 prompt → LLM 生成
```

### 项目里的完整实现
1. **解析**：优先 doc-processor（保留标题层级/表格），不可达时降级 Tika 纯文本。
2. **质量门禁**：`cleanScore` 过低直接隔离（QUARANTINED），不污染知识库。
3. **柔性分块**：`StructureAwareChunker` 按标题结构分块，而非死板等长切分。
4. **向量化**：text-embedding-v3（1024 维）批量编码入库。
5. **检索**：混合召回 + 重排（见第 6 节）。
6. **引用**：每个 chunk 带 `[n]` 编号，答案可溯源。

### 进阶方向
- **分块策略**：递归分块、语义分块、父子分块（parent-child chunking）、文档结构化分块（按 Markdown 标题）。
- **重排序**：检索后再用 rerank 模型精排（Cross-Encoder 比双塔 embedding 更准但更慢）。
- **评估**：RAGAS 等框架做忠实度/相关性自动评测（本项目手写了命中率/越界/成本采集，是轻量版）。

## 3. Tool Calling（函数调用）

### 是什么
让 LLM 输出结构化指令来"调用"外部函数，而不是让 LLM 自己编数据。流程：LLM 决定调用哪个工具 + 参数 → 程序执行 → 结果回灌给 LLM 继续生成。

### 项目里的用法
```java
@Tool(description = "对指定订单发起退款…")
public String refund(@ToolParam(description = "订单号") String orderId, ...) { ... }
```
通过 `ChatClient.Builder.defaultTools(orderQueryTool, refundTool, ...)` 注册。

### 关键设计：读/写分离
- **只读工具**（查订单）直接执行；
- **写操作工具**（退款/改地址/发券）标 `@ConfirmRequired`，LLM 调用时不真正执行，而是落 pending 等坐席确认——**把"LLM 有权做什么"从代码层收窄**，这是 LLM 应用安全的关键思路。

### 进阶方向
- 工具描述（description）质量直接影响 LLM 是否"选对工具"，要写清楚触发时机和参数含义。
- 工具调用失败要有兜底（本项目查不到订单返回 `found=false` 防止 LLM 编造）。
- 复杂的多步工具调用可引入 Agent 编排（ReAct、LangGraph 式状态机）。

## 4. SSE 流式输出与 Reactor 响应式编程

### 是什么
- **SSE（Server-Sent Events）**：服务端向浏览器单向推送的 HTTP 协议，适合"逐字输出"的聊天场景（比 WebSocket 简单，只需 `text/event-stream`）。
- **Reactor**：Spring WebFlux 的响应式编程库，核心是 `Flux`（0..N 流）和 `Mono`（0..1），用链式操作符处理异步数据流。

### 项目里的用法
```java
// Controller 返回 Flux<ServerSentEvent<String>>
return chatService.streamAnswer(...)
    .onErrorResume(GlobalExceptionHandler::toSseError);
```
前端用 `EventSource` 监听 `citations` / `token` / `error` 事件。

### 关键坑（本项目踩过并已记录）
- **ThreadLocal 跨线程丢失**：SSE 的 `doOnComplete/doOnError` 跑在 Reactor 的 Netty 线程，`TenantContext`（ThreadLocal）读不到。**修法**：在请求线程捕获上下文为局部变量，显式透传。
- **SSE 异常处理**：`produces=text/event-stream` 后 Content-Type 已锁定，`@RestControllerAdvice` 不能再返回 JSON，要用 SSE `event:error` 返回。
- **流式降级**：只在第一个 token 之前失败才切备用模型，否则会输出重复内容。

### 进阶方向
- Reactor 操作符：`map/flatMap/concat/merge/onErrorResume/retryWhen`、背压（backpressure）。
- 对比：WebSocket（全双工）、gRPC streaming、WebTransport。

## 5. pgvector：PostgreSQL 里的向量检索

### 是什么
pgvector 是 PostgreSQL 扩展，加了 `vector` 类型和相似度算子，让普通 PG 也能存向量、做近似最近邻（ANN）检索，避免单独维护一个向量数据库。

### 关键 SQL
```sql
-- 建列（1024 维）
embedding vector(1024)
-- 余弦相似度检索
SELECT * FROM vector_store ORDER BY embedding <=> query_vector LIMIT 10;
-- 索引（HNSW 是主流 ANN 算法）
CREATE INDEX ON vector_store USING hnsw (embedding vector_cosine_ops);
```

### 项目里的用法
`PgVectorStore` 存每个 chunk 的向量 + metadata（doc_id/chunk_index/source/kb_id），检索时用 `COSINE_DISTANCE` 距离 + metadata 过滤（按 doc_id、kb_id 过滤）。

### 坑
- **距离类型**：`<=>` 余弦距离（越小越相似）、`<->` L2、`<#>` 内积，选错会导致"越相似的排越后"。
- metadata 建议 JSONB，支持 `metadata->>'doc_id'` 过滤和查询。

## 6. 混合检索：向量 + BM25

### 是什么
- **向量检索**：语义相似，能召回"换个说法"的内容，但对专有名词/精确词不敏感。
- **BM25**：关键词精确匹配（TF-IDF 的现代版），对"ORD-1001""7天"这类精确词命中准，但不懂同义。

两者互补，混合召回（hybrid search）通常是 RAG 质量的分水岭。

### 项目里的用法
`RetrievalPipeline` 双路召回：PgVector 语义召回 + 过程内 BM25 索引关键词召回，合并去重后交给 LLM。

### 进阶方向
- **RRF（Reciprocal Rank Fusion）**：融合两路排名的经典算法，比简单拼接更优。
- 可选重排模型（reranker）做第三层精排。

## 7. Embedding 与语义聚类

### 是什么
- **Embedding**：把文本映射为高维向量，语义相近的文本向量距离近。
- **余弦相似度**：`cos(A,B) = A·B / (|A||B|)`，值越接近 1 越相似。

### 项目里的用法：未命中问题语义聚类
知识库答不上来的问题（检索未命中）是"该补什么文档"的金矿。但用户问法五花八门，字面聚合会把同义问题拆散。于是：

```
未命中 query 列表
 → embedding 编码（text-embedding-v3）
 → 贪心聚类：每个 query 与已有簇的质心算余弦，≥ 阈值(0.82)归入，否则新建簇
 → 每簇选代表问题 + 成员数，落 rag_gap_cluster 表
```

这样"7天无理由""过了7天还能退吗"聚成一类，反映的是**知识盲区**而非字面重复。

### 进阶方向
- 聚类算法：K-Means、DBSCAN、层次聚类（贪心是最简单的一版）。
- 降维可视化：t-SNE / UMAP 把高维向量画到 2D 平面看分布。

## 8. LLM-as-Judge（用模型监督模型）

### 是什么
用另一个 LLM 充当"裁判"，判断主模型输出是否符合要求。常用于评估和护栏。

### 项目里的用法：事实一致性护栏
回答生成后，把「回答」和「检索到的知识库片段」一起交给裁判模型，让它判断回答是否忠实于知识库、有没有凭空捏造。FAIL 则降级话术转人工。

```java
// 用 BeanOutputConverter 约束输出为结构化 JSON
系统提示：你是事实一致性裁判…只输出 JSON，verdict 取 PASS 或 FAIL
```

### 坑
- **结构化输出**：让 LLM 输出 JSON 要用约束（`BeanOutputConverter` / JSON mode），否则解析易崩。
- **裁判也会失效**：裁判模型本身挂了（如 403 配额超限），要降级放行 + 标记，不能让护栏崩溃拖垮主流程。

### 进阶方向
- 双裁判/多次采样取多数票降低裁判噪声。
- 用更强的模型当裁判（裁判模型通常要 ≥ 被裁判模型）。

## 9. 多模型管理与降级

### 是什么
生产环境不该只绑一个模型：主模型挂了、额度耗尽、限流时，要能自动切备用模型。

### 项目里的用法
- **角色分工**：glm-5.2 负责对话 + 判定类任务（改写/状态提取/护栏），text-embedding-v3 负责向量，DeepSeek-V3 作可选降级。
- **FallbackChatModel**：主模型失败时切备用，配合 `DegradationFlags` 标记"已降级"。
- **RetryTemplate**：只对瞬时错误（5xx/429/超时）指数退避重试，对 `NonTransientAiException`（401/403 认证/配额）**不重试**（重试也没用）。

### 进阶方向
- 多模型路由：按任务难度/成本/延迟路由到不同模型。
- 熔断器模式：连续失败后短暂熔断，避免雪崩。

## 10. 前端：Vue3 + EventSource + Markdown

### 关键技术点
- **Vue3 组合式 API**：`ref/computed/watch/onMounted`，`<script setup>` 语法糖。
- **EventSource**：原生 SSE 客户端，监听 `token` 事件逐字追加、`citations` 事件拿引用、`error` 事件拿错误。
- **Markdown 渲染**：markdown-it，`html:false` 禁用原始 HTML 防 XSS。
- **引用可点击**：渲染后的 HTML 里把 `[n]` 替换成带 `data-ref` 的上标，用**事件代理**（`document.addEventListener('click')`）统一处理——因为 `v-html` 注入的元素无法直接绑 `@click`。

### 体验细节（本项目实现的）
- 输入框高度自适应 + Enter 发送 / Shift+Enter 换行 + 中文输入法组词不误发。
- 智能滚动：用户上滑时暂停自动滚动，出现"回到底部"按钮。
- 错误友好提示：把 403 配额超限等后端错误转成人话 + 重试按钮。

### 进阶方向
- 流式渲染性能：大量 token 时避免整段重新渲染（本项目直接字符串拼接足够）。
- 代码高亮：集成 highlight.js / Prism。
- 虚拟滚动：超长会话历史。

## 11. 工程实践：ThreadLocal、幂等、可观测性

这三个是 LLM 应用工程化的"基本功"，本项目都有落地。

### 11.1 ThreadLocal 上下文
`TenantContext`（商家）+ `PlatformContext`（渠道）用 ThreadLocal 在请求线程传递，`ContextInterceptor` 在进入时 set、离开时 remove。

> **大坑**：ThreadLocal 不跨线程。响应式/流式回调跑在别的线程上，必须显式透传，否则拿到 null。本项目在 SSE 流式落库时踩过（platform 全落 unknown），修法是请求线程捕获后显式传参。

### 11.2 幂等
- **确认护栏**：同会话同参数重复请求返回同一条 pending（幂等键）。
- **写操作**：行级 `UPDATE ... WHERE status='pending'` 原子抢占，防止双击重复执行。
- **知识库上传去重**：同源文件重复上传先删旧文档再入库（覆盖语义）。

### 11.3 可观测性（三段式日志）
每个 HTTP 请求：
```
--> [GET] /chat/stream ...          # 入口
<-- [GET] /chat/stream 2345ms 200   # 出口 + 耗时 + 状态码
!!! 异常（含完整堆栈）              # 异常
```
原则：**入口/出口成对、异常必带堆栈、敏感信息脱敏**。LLM 应用最怕"静默失效"，日志 + 降级标志（DegradationFlags）就是它的照妖镜。

## 学习路径建议

1. **先跑起来**：按 `docs/启动指南.md` 起服务，传一份文档，问一个问题，观察完整链路。
2. **读核心编排**：从 `ChatService.streamAnswer` 入手，逐行看一条消息怎么流转。

4. **动手改**：加一个新工具、换一种分块策略、加一个降级标志——LLM 应用的能力是"改"出来的。
